This is a candid engineering assessment. The core finding is that the project is partly feasible—but only if you accept a quality ceiling far below hand-animated YouTube videos. The real bottleneck is not animation or LLM speed, but the deterministic translation of open-ended spatial language into geometrically correct, collision-free scenes. The "LLM as director, solver as cinematographer" split you propose is exactly right and is the only realistic path.

1. Is this feasible live and open-ended under these constraints?
Partly. The 2–3 second latency budget and 4 GB hardware are achievable. The open-ended correctness is not fully achievable today; you will need to accept frequent, visible errors on complex sentences.

What is proven today:

LLM → validated JSON scene graph: This works reliably with Groq-class models and is already a standard pattern.

Deterministic 2D layout with constraint solving: Proven in UI/layout engines and early scene-layout work. You can guarantee no overlaps and attach points for on, under, inside, holding.

2D skeletal animation at 60 fps in a browser: PixiJS, Rive, or Spine can handle a dozen stick figures on CPU-only laptops.

Pre-authored or procedurally generated walk/run/sit cycles: These are deterministic and fast.

What is research / hope:

Correct attachment for open-ended verbs and object shapes. Attaching a rider to a horse requires knowing the horse's saddle point, the rider's hip offset, and the leg configuration. A generic "sitting" IK pose will often look wrong on novel objects.

Text-to-motion generation fast enough for a 2–3 s budget on CPU. MoMask can run on CPU, but its first-run latency is around 10 s per prompt, and Kimodo takes about 2 minutes because of text encoding. Neither fits your real-time constraint without heavy caching and a very small verb vocabulary.

Cinematic storytelling quality from a scene graph. The difference between "a figure near a tree" and "Newton sitting under the apple tree, looking up, surprised" is not a single JSON field—it is a chain of poses, look-at targets, and secondary motion that a solver must infer.

2. The real hard problem: sentence → correct picture
Your guess is correct. The hard problem is spatial and functional relations, not noun recognition or animation speed. The failure you saw with "rider beside the horse" and "bird on the ground" is the default outcome of a regex parser. An LLM scene graph helps, but it only names relations; it does not know geometry.

The solution is a strict three-layer pipeline:

Semantic layer (LLM): Outputs only entities, verbs, and relations such as {subject: "Newton", relation: "under", object: "apple_tree"}, {subject: "apple", relation: "falling_onto", object: "Newton.head"}, {subject: "Newton", verb: "sit", on: "ground"}. The LLM must be forbidden from emitting coordinates or rendering code.

Geometric solver (deterministic): Converts relations into anchor points and constraints. For under, place the subject below the object's canopy region and above the ground plane. For falling_onto, compute a ballistic path ending at the target's head anchor. For holding, solve a two-bone IK arm so the hand reaches the prop's grip point. For riding, attach the rider's hip to the saddle anchor and pose the legs into a straddle. This solver is where 80% of your engineering effort belongs.

Motion layer (deterministic): A small verb library maps to pre-authored or procedurally generated cycles (walk, run, sit, point, fall). The LLM never invents motion curves; it only selects verbs from the closed list.

Without this strict split, you will reproduce the same failure mode: nouns right, relations wrong.

3. Best concrete stack under your constraints
Renderer: PixiJS is the safest choice for a 4 GB CPU-only laptop. It is a 2D WebGL/Canvas renderer with excellent performance for dozens of sprites and skeletal meshes. Rive is a strong alternative if you can accept a commercial runtime license and a more complex authoring workflow; its files are tiny and it has a state machine for character animation. Spine is more powerful for complex rigs but heavier. Avoid Lottie for dynamic IK-driven characters; it is best for fixed UI motion.

Motion: Do not rely on real-time text-to-motion generation. Use retrieval from a small, licensed motion library plus procedural cycles. MoMask's CPU path is too slow for the first call, but it could be used offline to generate a bank of stick-figure clips that you then retarget and cache. The licensing of HumanML3D/AMASS is a serious blocker: the motion data is academic/research only, and commercial use is not permitted without separate licensing from the Max Planck Institute. If this is a commercial product, you must either build your own mocap set or use a permissive motion library.

Layout solver: Implement your own constraint solver, or adapt the open approach from the "Relational Scene Layout" pattern: dependency-ordered placement, collision relaxation, and safe-area clamping. This is a few hundred lines of Python/TypeScript and is deterministic.

LLM: Groq with a Llama/gpt-oss class model is fine for the semantic layer. Enforce a strict JSON schema with pydantic or zod validation. The model should see only the current line and a compact memory of the previous scene graph, not the full history.

Expected latency on 4 GB CPU-only:

STT: Already local Whisper; leave it on GPU if available, otherwise use a small CPU Whisper model.

LLM call: 1–2 s per line on Groq.

Solver: < 50 ms for a small scene.

Animation: 60 fps for a dozen 2D stick figures in PixiJS.

Total: ~2–3 s, but the LLM latency is the tightest link. If Groq is slow, the scene will appear late.

4. Honest quality expectation
This will look like a simple stick-figure explainer, not a hand-animated YouTube stick-figure video. The poses will be correct for common verbs (walk, sit, point, fall) but stiff for nuanced actions (look up, surprised, work day and night in a cold shed). Famous-person caricatures are feasible only if you have a small offline set of heads; composing them from attributes will look generic and often wrong.

The animation will feel live and responsive, but it will not have the timing, secondary motion, and comic exaggeration that human animators add. Think of it as a diagram that moves, not a cartoon.

5. Which sentences will look right and which will fail
Sentence	Verdict	Reason
"Newton was sitting under an apple tree."	Likely pass	under is a simple anchor: place the figure below the canopy, above the ground. A sit cycle is standard. The tree asset can come from an offline SVG library with a defined canopy region.
"An apple fell on his head."	Marginal	The ballistic path is easy, but the hit reaction ("he looks up, surprised") requires a look-at IK and a facial expression state. Without a dedicated reaction clip, it will look mechanical.
"Napoleon's army crossed the Alps in winter."	Fail	"Army" is a collective noun; the solver must decide how many figures, their formation, and the mountain crossing path. "In winter" requires a background/weather state that the LLM cannot geometrically resolve. This will look like a few figures standing near a mountain.
"Marie Curie worked day and night in a cold shed."	Fail	"Worked" is too abstract for a verb-to-motion mapping. "Day and night" requires a time-lapse or lighting change that is outside the per-line scene graph. "Cold" is an atmosphere, not a spatial relation.
"The drop of water rises into the clouds."	Marginal	The path is a simple upward curve, but "rises into" requires the cloud to have an inside or enters anchor. If the cloud asset has a defined interior region, it can work; otherwise the drop will stop at the cloud's edge.
"The boy rode his horse to the village."	Marginal to pass	riding is solvable with a saddle anchor and a straddle pose. The motion along a path to a village is easy. The hard part is the horse's gait and the rider's bobbing; without a pre-authored gallop cycle, it will slide.
"Einstein said to his friend, time is relative."	Fail	Speech is handled by a bubble, but "said to his friend" requires a look-at and a talk cycle. The content ("time is relative") cannot be visually represented by the solver; it will be a bubble with text, which you already rejected as insufficient.
The pattern is clear: concrete physical relations and common verbs pass; collective nouns, abstract actions, atmosphere, and dialogue content fail.

6. The smallest proof (1–2 days)
Do not build the full pipeline first. Spend two days on a single hard sentence and a single failure sentence.

Day 1:

Hard-code one scene graph for "Newton was sitting under an apple tree" in JSON.

Build a minimal solver that places a stick figure at the tree's under anchor and plays a sit cycle.

Render it in PixiJS at 60 fps on a CPU-only laptop.

Then try "Napoleon's army crossed the Alps" with the same solver. The goal is to see it fail visibly and understand exactly which relation or entity type your solver cannot handle.

Day 2:

Add the LLM call for that one sentence and validate the JSON.

Measure the total latency from sentence end to first animated frame.

If the latency is over 3 s, or the under placement is visibly wrong, you have your answer: the approach needs a different solver or a narrower domain.

The proof succeeds if the Newton sentence looks plausibly like a stick figure sitting under a tree and the Napoleon sentence fails in a diagnosable, non-catastrophic way. It fails if even the Newton sentence requires hand-tuned coordinates.

7. Existing open-source projects to reuse
Relational Scene Layout (Hugging Face Space / docs): Implements exactly the LLM-as-director, solver-as-cinematographer split you need. Reuse the relational contract (left_of, inside, between, etc.) and the collision-relaxation solver pattern.

Stick-Gen (GitHub: gestura-ai/stick-gen): A dual-phase stick-figure animation model. It is not real-time on CPU, but it includes a motion-to-stick-figure renderer, a 42-action vocabulary, and AMASS/HumanML3D converters that you can study or use offline to build your motion bank.

MoMask ONNX CPU Space: Useful as an offline motion generator for building cached clips, not for live inference. Its first-call latency is too high.

Beatoven: Generates animation code from prompts using libraries like GSAP and Lottie. It is not a real-time scene-graph solver; it is more of a code-generation layer. You can borrow its hierarchical plan concept but not its runtime.

MotionCanvas / generic scene interpreter: The Relational Scene Layout doc references a generic.tsx interpreter that maps verbs (draw, move, trace, grow) to motion. This is a useful pattern for your verb library.

Final verdict: Build the deterministic solver first, keep the LLM strictly semantic, and narrow the domain to concrete physical actions with clear spatial relations. Accept that many sentences will produce a "near miss" rather than a correct picture. If you can live with that, the latency and hardware constraints are achievable. If you need hand-animated quality on every sentence, this is not feasible under these constraints today.
