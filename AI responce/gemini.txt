The Root Problem:
You are chasing literal visual representation (a unique AI drawing for every noun) instead of semantic visual representation (the way 3Blue1Brown or Kurzgesagt actually works). Explainer videos use abstraction, standardized modular assets, and uniform aesthetics to explain concepts.

2. Possible Architectures (Evaluated)
Here are 4 distinct ways to solve the "Asset + Animation" layer.

A. The "Kurzgesagt 3D" Approach (Low-Poly + Cel Shading + Semantic Search)
How it works: You use a 3D engine (Three.js). You apply a post-processing Cel-Shader (toon shader) with thick black outlines and unlit flat colors. This makes 3D look like 2D vector art. Characters are standard 3D humanoid rigs (Mixamo). Props are pulled dynamically from a massive pre-downloaded library of CC0 low-poly assets using local CPU vector search.

Quality: Very high. Consistent perspective, perfect lighting/style matching, real physics.

Latency/VRAM: Sub-100ms render. Zero VRAM cost for generation.

Risk: Requires managing a large static asset library.

B. The "Manim + Noun Project" Approach (Programmatic 2D Vector)
How it works: Expand on 3Blue1Brown's Manim. The scene is purely abstract mathematical vectors. Characters are simple geometric blobs (like Pi creatures). Props are fetched via API from a massive SVG icon database (e.g., Noun Project) and automatically re-colored to match your palette.

Quality: Academic, minimalist, highly professional.

Latency/VRAM: Ultra-fast. CPU/RAM only.

Risk: Cannot do complex physical interactions (e.g., a character physically grasping an intricately shaped prop).

C. The Modular 2D Rig Engine (Rive / Spine)
How it works: You use Rive (a real-time interactive 2D vector animation engine). You manually build 3 "Base Characters" with state machines (Walk, Run, Jump, Point). The LLM simply triggers state transitions in the Rive runtime.

Quality: Flawless 2D animation.

Latency/VRAM: Near-zero.

Risk: Highly limited open-vocabulary for props. You can't easily inject a random web image into a rigged Rive hand seamlessly.

D. The Fast Cloud Generative Storyboard (Future Paid Path)
How it works: LLM outputs a highly detailed prompt -> fal.ai (Cloud Flux/SDXL API at ~300ms/image) -> displayed on screen.

Quality: Beautiful, detailed images.

Latency/VRAM: ~1-2s over network. No local VRAM used.

Risk: Total loss of deterministic animation and physics. You get V3 (Story Scenes) but completely lose V2 (Canvas for Imagination/Physics).

3. Recommended Approach: Neuro-Symbolic 3D with Cel Shading
Keep: Whisper, Groq, Python Solvers, Pydantic, Three.js, JSON scene graphs.Drop: SD-Turbo, 2D Cutouts, Photo Background Removal, Generative AI for individual assets.

The Solution: Build a 3D world that renders as a 2D explainer video.

Uniform Aesthetics: Use Three.js with a Post-Processing Toon/Cel Shader. This flattens the 3D models into flat colors with outlines. Everything immediately looks like a cohesive 2D vector explainer video, regardless of where the asset came from.

Base Characters: Do not generate characters. Build or download 3 generic base character models (e.g., a plain humanoid mannequin, a stylized robot, a dog). Rig them using standard Mixamo animations (Walk, Push, Throw, Idle).

Semantic Prop Library (Open Vocabulary): Download a massive free 3D library (e.g., Kenney.nl, which has ~20,000 CC0 low-poly objects). Index their filenames/descriptions into a local vector database using a tiny CPU-based embedding model.

How it flows live: Teacher says "A man pushes a refrigerator." -> Groq outputs {action: "push", actor: "man", prop: "refrigerator"} -> CPU Embedding search finds props/appliances/fridge.gltf -> Three.js loads the Mixamo pushing animation and attaches the fridge GLTF to the hand bone -> Python solver applies friction and velocity vectors.

Why this works: It perfectly marries your deterministic physics solvers with high-quality, continuous animation.

4. Concrete Tools & Stack
Current (Free / 4GB VRAM) Path:

STT: Faster-Whisper tiny.en or base.en (free up VRAM; medium is overkill for classrooms with good mics).

LLM: Groq API (Llama 3 8B or 70B). Fast, free tier is sufficient for small JSON schemas.

Prop Library: Kenney.nl (Game assets). Absolutely free, CC0, thousands of stylized, low-poly models (buildings, vehicles, furniture, nature, space).

Character Rigs: Mixamo (Free Adobe tool). Upload a basic humanoid mesh, it auto-rigs and gives you hundreds of animation clips (FBX/GLTF format).

Semantic Search (CPU): sentence-transformers running all-MiniLM-L6-v2. Takes <100MB of RAM. Run a cosine similarity search against the Kenney asset list to map "spear" to weapon_polearm.gltf.

Rendering: Three.js + OutlinePass / CustomShaderMaterial to achieve the vector look.

Paid / Future Path:

LLM: GPT-4o-mini or Claude 3.5 Haiku (better JSON following, fewer 429 errors).

Generative Assets: Use an API like Meshy.ai or Tripo3D to generate 3D GLTF props on the fly in ~5 seconds if a prop isn't in your local DB.

5. Handling "Open Vocabulary" Fallbacks
What happens if the teacher says "A flux capacitor"? The local embedding search might yield a low confidence score (e.g., matches with "battery").

The Explainer Method: If confidence is below a threshold (e.g., 0.6), spawn a generic primitive (a minimalist glowing cube or a flat cardboard box) and use a Three.js text label floating above it that says "Flux Capacitor".

This is an established educational trope. It keeps the physics solver working (a cube has collision bounds), keeps the style clean, and admits to the students what the object represents without breaking immersion.

6. The LLM Scene Schema (Optimized for Tokens/Speed)
Keep it flat, semantic, and decoupled from math. Let Groq be the "Director" and Python be the "Animator".

JSON
{
  "intent": "simulation", // or "story", "slides"
  "environment": {
    "gravity": 9.8,
    "setting": "surface" // triggers default floor
  },
  "entities": [
    {
      "id": "e1",
      "type": "character",
      "concept": "human man",
      "position": "left"
    },
    {
      "id": "e2",
      "type": "prop",
      "concept": "heavy wooden box",
      "position": "center"
    }
  ],
  "relations": [
    {"subject": "e1", "verb": "pushing", "object": "e2", "force_vector": "right"}
  ],
  "annotations": [
    {"target": "e2", "type": "arrow", "label": "Friction", "direction": "left"}
  ],
  "camera": {"focus_on": "e2", "zoom": "medium"}
}
Notice: The LLM does not output coordinates (x: 1.45). It outputs semantic layout ("left", "center"). Your Python deterministic engine translates "left" to -5.0 on the X-axis based on the screen size.

7. Practical Build Order & Success Test
Week 1: The Render Core. Setup Three.js with a Toon Shader. Place a sphere and a cube. Make sure it looks like 2D flat art. (If you skip the shader, it will look like a cheap 90s video game).

Week 2: The Actor. Import one Mixamo character (e.g., a crash test dummy). Hook up Idle, Walk, and Push animations triggered by keyboard presses.

Week 3: The Library. Download the Kenney asset library. Write a Python script to generate embeddings for all filenames. Build the fallback logic (labeled box).

Week 4: Integration. Connect Whisper -> Groq -> Semantic Search -> Three.js.

Success Test: Read exactly this: "A man pushes a large boulder. He stops. The boulder slides and slows to a halt." If it looks like a cohesive vector animation, and the physics math holds up, you have succeeded.

8. Research Novelty (The Publishable Angle)
For your IEEE paper, your novelty is "Real-Time Neuro-Symbolic Translation for Educational Animation."

Most research focuses on either end-to-end video generation (Sora, Runway) which hallucinate physics, or strict programmatic animation (Manim) which requires coding.

Your novelty is the bridging architecture: using an LLM to parse continuous live speech into a discrete semantic graph, mapping open-vocabulary nouns to a bounded geometric asset library via latent space (embeddings), and feeding the result into deterministic differential equation solvers for physically accurate live rendering.

9. System Architecture (V2 & V3 Sharing)
Audio Pipeline (GPU): Mic -> faster-whisper -> Text Stream.

Director (Cloud): Text Stream -> Groq LLM -> JSON Scene Graph.

Asset Mapper (CPU): Concept -> all-MiniLM-L6-v2 -> Local ID or Fallback Box.

Physics Engine (CPU): Python solvers calculate kinematics frame-by-frame based on the Scene Graph. Emits a WebSocket stream of coordinates/rotations/animation_states.

Renderer (Browser): Three.js receives WebSocket coordinates. Renders 3D assets with Cel Shading.

V2 vs V3: They share 100% of the above. V2 uses the Physics Engine to update coordinates. V3 bypasses the Physics Engine and uses a Cinematic Engine (simple keyframe easing for pans, fades, and walking across the screen without physical collision math).

10. Traps and Mistakes to Avoid
Trap: Trying to map every word perfectly. If the teacher says "A 1994 Toyota Corolla", your semantic search will yield "car". Just render the car. Do not try to prompt an image generator to get the exact model—it will break visual consistency.

Trap: Relying on the LLM for state. Do not send the whole transcript to Groq. Keep a "World State" in Python. Send Groq the current world state JSON + the new sentence, and ask it for mutations (add, remove, change state).

Trap: Waiting for the end of a sentence. Use streaming STT. Have a fast, local NLP script that detects nouns/verbs before the LLM call to pre-warm the asset loader (fetch the 3D model into RAM before Groq even finishes parsing the JSON).
