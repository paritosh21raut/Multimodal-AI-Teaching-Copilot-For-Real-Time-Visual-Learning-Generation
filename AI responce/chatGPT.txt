# Recommended design: a small action language, not a large animation vocabulary

Your architecture is now much more promising because you have separated three things:

1. Language: What happened?
2. Choreography: What movements and interactions are required?
3. Execution: Where do the characters and objects move?

I would preserve that separation.

My biggest recommendation is to introduce a distinction between primitive operations, composite actions and world-state changes.

Do not make every English verb a new low-level operation. Equally, do not reduce every verb to `move_to + react + attach`. Some actions have their own interaction mechanics.

For example, `give`, `hug`, `fight` and `climb` have distinct choreography. They should be recognized as semantic actions, but compiled into reusable, deterministic action graphs.

This gives you an extensible vocabulary without creating a different animation implementation for every story.

# 1. The 25 additional operations I recommend

Your existing vocabulary already covers basic movement, posture, attachment, falling, throwing, speaking and reactions.

I would add the following 25, ranked by expected coverage across ordinary moral stories, folk tales, history and science anecdotes.

The ranking is an engineering prioritization, not a measured frequency analysis.

## Priority 1: Essential interactions

Implement first

| Rank | Operation  | What it should do                                    | Why it matters                          |
| ---- | ---------- | ---------------------------------------------------- | --------------------------------------- |
| 1    | `pick_up`  | Move hand to object, grasp and attach                | Extremely common interaction            |
| 2    | `put_down` | Release object at a valid surface or location        | Completes object manipulation           |
| 3    | `push`     | Apply directional movement to an object or character | Doors, carts, people, objects           |
| 4    | `pull`     | Pull target towards actor                            | Ropes, carts, doors, people             |
| 5    | `transfer` | Transfer possession between two characters           | Give, hand, pass, receive               |
| 6    | `pursue`   | Follow, chase or flee from another entity            | Animal tales, adventures, history       |
| 7    | `turn_to`  | Rotate character body towards direction or target    | Natural-looking interactions            |
| 8    | `jump`     | Generate a jumping trajectory and landing            | Obstacles, animals, excitement          |
| 9    | `climb`    | Alternate hand/foot contacts while progressing       | Trees, mountains, ladders               |
| 10   | `hide`     | Move into a concealment region and become occluded   | Moral stories, folk tales, chase scenes |

A particularly important design decision:

`pick_up` and `put_down` should be semantic operations that expand into your existing `attach` and `detach`.

They are not new physics systems.

For instance:

```
pick_up(person, apple)
    → move_to(person, apple)
    → reach_hand_to(apple)
    → attach(person.right_hand, apple)
    → change_posture(person, standing)
```

The compiler should skip unnecessary movement when the character is already next to the object.

## Priority 2: Everyday and animal activities

Implement second

| Rank | Operation    | What it should do                                     |
| ---- | ------------ | ----------------------------------------------------- |
| 11   | `eat`        | Bring food to mouth, bite, chew                       |
| 12   | `drink`      | Attach vessel to hand, tilt towards mouth             |
| 13   | `read`       | Hold/open reading material, orient eyes towards it    |
| 14   | `write_draw` | Hand movement over paper, board or surface            |
| 15   | `open`       | Move a door, lid or container around its hinge/anchor |
| 16   | `close`      | Reverse the opening movement                          |
| 17   | `search`     | Scan a region with gaze and body movement             |
| 18   | `swim`       | Animate limbs and translate through a water region    |
| 19   | `fly`        | Airborne movement with wing or body animation         |
| 20   | `rest`       | Sleep, lie down or wake through a state transition    |

`fly` and `swim` should be locomotion modes, not entirely separate skeletal animation architectures.

A bird, a butterfly and a flying human need different movement profiles, but they can all use the same high-level translation/path interface.

Similarly, `rest` can contain subtypes:

```
{
  "op": "rest",
  "actor": "person_1",
  "mode": "sleep"
}
```

Waking can be represented by changing the rest state to `awake`, followed by a posture transition.

## Priority 3: Composite activities

Implement after the core

| Rank | Operation | What it should do                                             |
| ---- | --------- | ------------------------------------------------------------- |
| 21   | `cook`    | Combine ingredients, manipulate cooking tools, wait, serve    |
| 22   | `build`   | Assemble components through repeated placement and attachment |
| 23   | `hug`     | Two-character synchronized interaction                        |
| 24   | `fight`   | Coordinated attack, block, dodge and reaction choreography    |
| 25   | `break`   | Change an object's state, optionally animate fragmentation    |

These five are particularly important because they expose the limitations of a simple operation list.

They require multiple synchronized actions, object-state changes or interaction-specific constraints.

### Operations I would deliberately postpone

Do not add every conceivable verb immediately.

Some useful candidates for a later release are:

- Rescue
- Plant
- Harvest
- Wash
- Clean
- Repair
- Buy
- Sell
- Rescue
- Celebrate

Many of these can initially reuse the operations above.

For example, planting can be expressed using `dig`-like movement, `pick_up`, placement and a plant-growth world-state transition. You don't need an entirely new skeletal animation system.

# 2. How composite verbs should map to operations

My recommendation is a three-level action architecture.

Level 1: Semantic action

# GIVE

What the teacher said

Level 2: Choreography graph

Approach → Reach → Release → Receive

Which interactions must happen

Level 3: Primitive execution

move_to · attach · detach · change_posture · react

How the engine executes the interaction

The LLM should output semantic actions, not choreographed sequences.

The deterministic compiler should expand those actions using predefined, parameterized choreography graphs.

This is not a story template. It is an action grammar.

## A. Give

Sentence:

"The king gave his sword to the soldier."

Semantic operation:

```
{
  "op": "transfer",
  "actor": "king",
  "target": "soldier",
  "object": "sword",
  "mode": "give"
}
```

Execution:

1. Identify which character currently holds the sword.
2. Ensure both characters can reach each other.
3. Move the sword-holding hand towards the recipient.
4. Move the recipient's hand to the sword's grip anchor.
5. Transfer attachment ownership.
6. Release the donor's hand.
7. Show the recipient holding the sword.

The important part is that the sword must never float between the two characters.

Implement transfer as an atomic transaction: if the receiving attachment cannot be established, retain the existing owner rather than silently losing the object.

## B. Chase

Sentence:

"The wolf chased the rabbit."

Do not generate two independent `move_to` operations.

That can make the wolf run towards the rabbit's initial position while the rabbit runs elsewhere.

Instead, use a pursuit controller.

```
{
  "op": "pursue",
  "actor": "wolf",
  "target": "rabbit",
  "mode": "chase",
  "speed": "fast",
  "maintain_distance": false
}
```

The rabbit gets an escape behaviour, either explicitly stated or inferred with lower confidence.

The controller continuously updates the wolf's destination using the rabbit's current position.

The same operation can support:

- Follow: maintain a comfortable distance.
- Chase: reduce distance.
- Flee: increase distance from a threat.

The distinction belongs in `mode`, not separate locomotion architectures.

## C. Hug

Sentence:

"The mother hugged her child."

This deserves its own composite choreography.

Execution:

- Both characters turn towards one another.
- They move into a suitable interaction distance.
- Their torsos and arms move into a paired pose.
- The arms establish contact at the appropriate torso anchors.
- Hold the pose briefly.
- Release and return to their previous states.

A hug is a synchronized two-character constraint, not simply two independent people moving towards one another.

## D. Fight

Sentence:

"The two warriors fought."

Treat this as a choreographed interaction between two characters.

Possible sequence:

```
approach
  ↓
face_each_other
  ↓
attack ↔ block
  ↓
dodge ↔ react
  ↓
separate
```

Use alternating action tracks.

One character attacking and the other blocking should happen at compatible times.

Start with non-graphic, exaggerated stick-figure fighting. You do not need realistic combat simulation.

Do not use actual collision forces to determine the entire fight. A deterministic choreography graph will be much easier to control.

## E. Climb

Sentence:

"The boy climbed the tree."

This deserves a specialized movement controller because ordinary walk cycles cannot produce correct climbing.

The character needs:

- Hand contact points along the trunk.
- Foot contact points.
- Alternating limb movement.
- Root translation upward.
- Body orientation towards the trunk.

A climbable object needs an explicit `climb_surface` with available contact locations.

## F. Cook

Sentence:

"The woman cooked rice in a pot."

Compile the semantic action into a task graph:

1. Move to cooking area.
2. Identify the pot.
3. Attach ingredient to hand.
4. Transfer ingredient into pot.
5. Hold or move a stirring utensil.
6. Animate stirring.
7. Show cooking effects.
8. Change food state to cooked.

A `cook` graph should accept different ingredients, containers, tools and cooking methods.

You should not need a separate implementation for rice, soup and vegetables.

## G. Build

Sentence:

"The workers built a house."

This is a particularly important composite action because the object itself changes over time.

Use a construction task graph:

1. Create an incomplete construction state.
2. Select a building component.
3. Move it to its placement region.
4. Attach it to the structure's anchor.
5. Repeat.
6. Transition the structure to its completed state.

You don't need to animate every brick. A few meaningful components can communicate the construction process.

### My rule for deciding whether a verb deserves a new operation

Ask three questions:

1. Does it require a unique physical constraint?
2. Does it require coordination between multiple entities?
3. Does it have a meaningful state transition that other operations cannot express cleanly?

When the answer is yes, give it a semantic composite action and a deterministic choreography implementation.

Otherwise, compose existing operations.

I would not optimize for the number of SVG files. I would optimize for the number of different story situations each asset enables.

For example, a tree enables:

- Sitting under a tree.
- Climbing a tree.
- Hiding behind a tree.
- Picking fruit.
- Birds sitting on branches.
- Cutting down a tree.

One properly authored tree asset provides more value than dozens of unrelated decorative icons.

## A crucial addition: environments should not be ordinary props

I would not count the following as individual props:

- Forest
- Village
- Laboratory
- Classroom
- Palace interior
- Mountain landscape
- Battlefield
- Seashore

These should be generated through an environment grammar.

For example, a forest is not a single background image. It is a collection of spatially arranged trees, bushes, rocks, ground and optional environmental effects.

A village is a collection of houses, pathways, trees and other structures.

That is how you avoid creating a separate template for every story.

# 4. Crowds, weather, indoor scenes and time skips

These are four different problems. I would not solve them using the same scene-graph mechanism.

## A. Crowds: introduce group entities

Do not make the LLM individually control 100 soldiers.

Introduce a `group` entity type.

Example:

```
{
  "id": "army_1",
  "type": "group",
  "category": "soldiers",
  "count": "large",
  "formation": "column",
  "movement": {
    "direction": "forward",
    "mode": "march"
  }
}
```

The compiler can represent this as:

- A few detailed foreground characters.
- Several repeated low-detail figures.
- Background silhouettes extending into the distance.
- A group-level movement controller.

## C. Indoor scenes: create a generic room-building system

This is more important than it initially appears.

Many ordinary stories happen inside a house, palace, laboratory, classroom, shop or shed.

I would create a general 2D room container.

[empty room with french window and furniture](https://images.openai.com/static-rsc-4/E_i8_zKvZtg3awrQ1K6f93cjBPsmBxU75dJmvRYVolp0e4GFV1j0qhIfSpqjOvOLBxi6WufWKimydRcWbsXcFCCTjYE7G1ttJZE1q_V-2qs-EA0Unv-zaNTYd4hifYp1_yY9rWcLMuxY1Aorn4PeLIV3yZs3ksFr0Tp5iujgUIB_MHBu3UTn3R2TQlbFjgXc?purpose=inline)

The room has:

- A floor plane.
- Back wall.
- Optional side wall.
- Door and window openings.
- Wall attachment points.
- Furniture placement regions.
- Lighting state.
- Foreground and background layers.

Objects receive semantic placement constraints.

Examples:

```
book → on(table)
person → sitting_on(chair)
painting → attached_to(wall)
cup → on(table)
person → in(room)
```

The compiler positions the furniture first and then places the characters.

Do not let the LLM assign screen coordinates.

The LLM should say:

```
{
  "room_type": "laboratory",
  "objects": ["table", "microscope", "chair"],
  "relations": [
    ["microscope", "on", "table"],
    ["scientist", "sitting_on", "chair"]
  ]
}
```

The room builder handles layout.

A laboratory, a kitchen and a bedroom can all use the same room engine with different objects and environmental metadata.

## D. Time skips: introduce a world-transition event

This deserves a separate concept.

Consider:

"The farmer planted a seed. Several months later, it had grown into a tree."

You should not animate several months in real time.

Instead:

1. The farmer plants the seed.
2. The scene holds briefly.
3. A transition begins.
4. A caption appears: "Several months later".
5. The seed changes into a growing plant.
6. The environment changes if appropriate.

I would introduce a world-level event such as:

```
{
  "op": "time_jump",
  "duration": "several_months",
  "transition": "dissolve"
}
```

This is not a character action. It changes the temporal state of the world.

Support:

| Temporal event       | Visual treatment                                 |
| -------------------- | ------------------------------------------------ |
| Later that day       | Lighting transition                              |
| At night             | Sun to moon, darkness                            |
| Next morning         | Dawn transition                                  |
| Several months later | Calendar/season transition                       |
| Many years later     | Time card, aged characters or changed structures |
| Long ago             | Historical atmosphere and time caption           |

For a year-long time skip, you can use a 0.5–1-second transition. The simulation time is compressed, while the resulting world state is updated.

Keep temporal state separate from actual animation time. Otherwise you will end up with confusing timelines.

# 5. How to measure coverage fairly on unseen stories

This is probably the most important part of the development process.

There is a serious risk of building an impressive demonstration that succeeds on 15 prepared stories but fails on ordinary classroom speech.

You need a benchmark that measures generalization, not memorization.

## A. Build a story benchmark

For your first serious evaluation, I recommend:

# 60 stories

Minimum proposed held-out evaluation set

# 20

Moral / folk

# 20

History

# 20

Science

Target approximately 600–800 annotated event clauses across the stories.

Examples of stories to include:

Moral and folk stories: The thirsty crow, the lion and the mouse, the tortoise and the hare, the honest woodcutter, unfamiliar folk tales.

History: Newton's apple anecdote, Napoleon crossing the Alps, historical journeys, battles, discoveries and meetings.

Science: Water cycle, discovery anecdotes, blood circulation, planetary movement, experiments and scientific inventions.

Do not make the test dataset consist only of famous stories.

Include original stories written by humans, stories paraphrased in unfamiliar language and combinations of familiar actions with unfamiliar objects.

### Dataset split

Keep three distinct sets:

| Set         | Purpose                                |
| ----------- | -------------------------------------- |
| Development | Tune the schema and compiler           |
| Validation  | Find regressions during implementation |
| Test        | Unseen stories, never used for tuning  |

Split by complete story, not individual sentences.

Otherwise, sentences from the same story can leak into both development and test sets.

Also separate:

- Ordinary combinations of known actions and objects.
- Unseen combinations of known actions and objects.
- Unfamiliar nouns and synonyms.
- Complex spatial relationships.
- Multi-sentence pronoun references.
- Ambiguous and metaphorical language.

I would deliberately include some sentences that the engine cannot fully represent. A system should not be rewarded for pretending to understand something it cannot animate.

## B. Evaluate atomic events, not just sentences

Consider:

"The king entered the castle, sat on his throne and gave his sword to the soldier."

This is one sentence but contains multiple events:

1. King enters castle.
2. King moves into throne area.
3. King sits on throne.
4. King transfers sword to soldier.

Evaluate each independently.

For each atomic event, assign:

| Score | Meaning                                                    |
| ----- | ---------------------------------------------------------- |
| 1.0   | Faithfully animated                                        |
| 0.5   | Partially represented, with the important meaning retained |
| 0.0   | Not animated or represented incorrectly                    |

A caption or labelled unknown-object box should count as a fallback, not a successful animation.

Track fallback separately so you know whether the failure was language understanding, asset retrieval or animation execution.

## C. Measure five separate dimensions

Do not report only one accuracy number.

1\. Semantic event coverage

What percentage of the story's meaningful events can your engine animate?

Target: ≥80% weighted event coverage.

2\. Spatial relationship accuracy

Does the character actually sit on the chair, ride the horse, hold the object and stand beneath the tree?

Target: ≥90% on supported relationships.

3\. Narrative continuity

Are pronouns resolved correctly? Are objects preserved across sentences? Do characters maintain their identities?

Target: ≥90% correct identity and state continuity on supported cases.

4\. Visual faithfulness

Does the animation communicate what actually happened?

Use independent human evaluators to score the rendered clips.

Target: ≥80% of tested lines rated at least 4/5 for faithfulness.

5\. Real-time performance

Measure the time from the end of the teacher's utterance to the first stable, meaningful animation.

Target: p95 latency ≤3 seconds, with at least 30 FPS on supported hardware.

Do not let a good average hide a weak genre. Report the metrics separately for moral/folk, history and science.

Also report results separately for familiar and unfamiliar action-object combinations.

## D. What should count as success?

My proposed release gates:

| Measurement                      | Minimum for an MVP  | Strong result |
| -------------------------------- | ------------------- | ------------- |
| Visually faithful event coverage | 75%                 | 85%+          |
| Supported relation correctness   | 90%                 | 95%+          |
| Identity/state continuity        | 90%                 | 95%+          |
| Human-rated visual faithfulness  | 4/5 on 80% of lines | 4/5 on 90%    |
| p95 end-to-end latency           | ≤3 seconds          | ≤2 seconds    |
| Minimum rendering performance    | 30 FPS              | 60 FPS        |

These are proposed engineering acceptance criteria, not established industry benchmarks.

I would add one more rule:

No individual genre should fall below 65% faithful event coverage, even if the overall score is high.

You do not want a system that works wonderfully for folk stories but cannot visualize scientific explanations.

### Separate the failure types

For each failed event, record one of these:

```
ASR_FAILURE
LLM_SEMANTIC_FAILURE
COREFERENCE_FAILURE
UNKNOWN_ACTION
UNKNOWN_ASSET
RELATION_FAILURE
LAYOUT_FAILURE
IK_FAILURE
MOTION_FAILURE
RENDER_FAILURE
LATENCY_FAILURE
```

This is important because otherwise you'll spend time improving the LLM when the real failure is an incorrect attachment anchor.

The registry should describe both what an object can do and what can be done to it.

For instance:

```
{
  "asset": "chair",
  "affordances": [
    "supports_sitting",
    "supports_object_placement"
  ],
  "anchors": {
    "seat": [0.5, 0.48],
    "ground": [0.5, 0.95],
    "backrest": [0.5, 0.18]
  },
  "constraints": {
    "supports_sitting": {
      "actor_anchor": "pelvis",
      "target_anchor": "seat"
    }
  }
}
```

The actual coordinates should come from your authored asset metadata.

This solves a problem that will otherwise appear repeatedly: a syntactically valid scene graph can describe a physically impossible interaction.

For example, an LLM might attempt to make a character ride a table. Your validator should reject the interaction because the table does not expose a riding affordance.

The engine should distinguish:

- Valid and executable.
- Semantically understood but unsupported.
- Physically invalid.
- Missing asset.

That is much better than blindly executing every JSON operation.

# 7. Final recommendation: what I would actually implement

I would prioritize the engineering work as follows:

| Phase | What to build                             | Exit condition                                                           |
| ----- | ----------------------------------------- | ------------------------------------------------------------------------ |
| 1     | 25 additional semantic operations         | Every operation has a defined schema and expected effects                |
| 2     | Action choreography compiler              | Give, chase, hug, climb, cook and build work without story-specific code |
| 3     | First 20 prop families                    | All essential anchors and affordances work                               |
| 4     | Persistent environment and group entities | Indoor, outdoor and crowd scenes work                                    |
| 5     | Weather and time transitions              | Global world-state changes work                                          |
| 6     | Full 40-family asset library              | Core story domains are represented                                       |
| 7     | Unseen-story benchmark                    | Meets the MVP release gates                                              |

One implementation detail I would strongly enforce: every operation needs declared preconditions, effects, duration and failure behaviour.

For example:

| Field              | `transfer`                                 |
| ------------------ | ------------------------------------------ |
| Preconditions      | Donor holds object; recipient is reachable |
| Initial state      | Object attached to donor                   |
| Intermediate state | Both hands reach the object                |
| Final state        | Object attached to recipient               |
| Failure            | Preserve donor attachment                  |
| Animation          | Approach, reach, handoff, release          |

This will make the engine debuggable and deterministic.

## My final verdict

I think the most promising part of your architecture is not the stick figure, the Groq model or even the SVG library.

It is the combination of:

A persistent world + typed actions + semantic affordances + deterministic choreography.

That is the foundation of a genuinely compositional animation engine.

And I would keep one principle above everything else:

> An animation that correctly represents a simple event is more valuable than a sophisticated animation that represents the wrong event.

For the first version, I would target 80% faithful coverage of ordinary, supported classroom stories, not an unrealistic promise to animate every possible sentence.

Build the language of interactions first. The visual world can grow on top of it.
