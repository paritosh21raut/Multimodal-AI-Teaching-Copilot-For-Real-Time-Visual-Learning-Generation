V2 "CANVAS FOR IMAGINATION" - WHAT WE WANT, WHAT WE TRIED, WHY IT FAILS
(Multimodal AI Teaching Copilot, written 2026-10-25)

1. THE PROJECT IN ONE PARAGRAPH
A laptop app listens to a live lecture (mic -> local speech-to-text) and shows a live educational display on the
projector. V1 (done, works): it builds slides live from what the teacher says. V2 is the next step: when the teacher
describes something, the app DRAWS AND ANIMATES it live on the slide.

2. WHAT V2 SHOULD DO (THE GOAL)
- Anything the teacher says becomes a picture/animation within ~2 s: things, places, people, actions, relations.
  Educational ("a block sliding down an incline", "an electron orbiting the nucleus", "rain falling on a walking
  man") and odd ones too ("a bicycle under the ocean", "a laptop flying on an airplane", "throw a book in the air").
- Looks like a YouTube explainer / textbook illustration: one consistent clean style (our "edu_flat_v1": flat
  colours, no outlines, fixed character palette), real relative sizes, characters that hold, push, throw, walk,
  with live faces (blink, expressions, talking), any camera angle, focus/zoom on a part.
- Physics must be correct: the LLM only says WHAT is in the scene; Python law solvers (motion, projectile, relative
  motion, fields, waves, rigid bodies) compute HOW it moves and every number shown. No hard-coded topic scenes.
- Continuity: the scene keeps building as the teacher keeps talking ("now he throws it harder").
- "Imagine Mode" button: every line is drawn until the teacher presses End, then back to slides.

3. HARD CONSTRAINTS
- Real time, live, on a laptop: RTX 3050, 4 GB VRAM, which already runs Whisper (STT).
- No paid APIs. LLM = Groq free tier (several keys, ~8k tokens/minute per model, 429 errors under load).
  Free cloud image tiers (Cloudflare Workers AI, HuggingFace) allowed; local models as fallback.
- LLM never controls flow, never writes code, never computes physics; context sent to it is bounded.

4. TOOLS / STACK
Python 3.10-3.12, FastAPI + WebSocket server, browser display page (HTML canvas/SVG, later three.js 0.160),
faster-whisper medium.en (GPU), Groq LLM (Llama models, JSON scene ops), pydantic contracts, Playwright (browser
tests + screenshots), pytest (~1800 tests). Pictures: Microsoft Fluent 3D emoji (MIT), Wikimedia/Openverse photo
search + CLIP ranking + u2netp ONNX background removal (cutouts), SD-Turbo (local image generation test),
reference art sheets generated by a WhatsApp AI chatbot.

5. WHAT WE TRIED, IN ORDER, AND WHY EACH FELL SHORT
a) S0-S4: 21 hand-built simulation TEMPLATES (incline, pendulum, circuits, waves, orbits, Bohr atom, heart, pH...).
   Works and is accurate, but only for topics we pre-built. Not "imagination". Kept as teacher-picked/auto on cue.
b) F-015 scene core: trigger words + topic "worlds" (geometry, plots, motion, relative motion). Accurate, but still
   limited to the worlds we coded; anything outside falls through.
c) F-016 C1 open canvas: LLM turns each line into scene ops (add thing/place, relation "on/under/holding", action
   "throw/fall/move"), drawn with 3D emoji + photo cutouts + backdrops, real-size table, focus camera. Runs live
   (line -> first shape ~2.1 s p50). PROBLEM: it looks like separate stickers pasted on a slide. Emoji/photos have
   one fixed pose, mixed styles, no actions (a man can't actually throw), wrong word sense, photos slow (~5 s).
d) Image generation (SD-Turbo local, cloud tested/planned): fast alone (0.41 s/image) but 11.6 s while Whisper
   shares the GPU; ignores style prompts, so every image looks different; characters drift between frames;
   can't produce consistent animation frames. Unreliable for a live, consistent, animated scene.
e) D1 style board: 7 code-drawn styles (stick, chalk, flat vector...). User rejected all as not good enough.
   Chose a reference style from WhatsApp-generated sheets instead.
f) D1b: build the character in code as a flat-unlit 3D model (three.js spheres/cylinders + canvas face).
   Motion, physics arrows and live expressions were GOOD (144 fps). Face, hair and body looked "very bad"; a second
   round of tuning made it worse. Hand-shaping 3D primitives to match 2D art does not converge.
g) D1c/D1d (current): 2D puppets cut from the reference sheets (body parts as separate images, rigged and animated
   by our engine, faces from expression sheets), 3D world kept for physics/camera. Side view looks like the sheet,
   but each view (front/side/back/top/8 angles) needs its own matching part sheets; the AI-made sheets drift in
   scale/colour/proportions and their joint data is wrong, so every part needs manual measuring and fixing.

6. THE ROOT REASONS WE KEEP FAILING
- Open vocabulary vs. assets: "draw anything" needs a picture for anything, in any pose, in one style. Fixed
  assets (emoji, photos, templates) cover only what exists; generated images cover anything but are inconsistent.
  No approach so far gives BOTH coverage AND consistency.
- Animation needs consistent, rigged characters/objects. Images (photos, emoji, AI images) are single frames; you
  can move them but not make them act. Rigs need art made for rigging, for every view, which we don't have.
- We have no artist/3D modeller and no rigged asset library; code-built art looks amateur.
- Hardware/quota: 4 GB VRAM shared with live STT; free LLM ~8k TPM; free image APIs slow/limited. Real time
  (~2 s) rules out heavy generation per line.
- Language is ambiguous; the LLM sometimes picks the wrong sense or layout, STT mishears words (spear ->
  "keyboard"), and odd combos have no "correct" picture to check against.
- Quality bar is subjective and high ("explainer video" look), so each round passes tests but fails the eye.

7. WHAT WE ARE STILL TRYING TO ACHIEVE / OPEN QUESTION
A reliable pipeline: teacher's sentence -> LLM scene graph (what/where/action) -> Python laws (how it moves,
exact numbers) -> our renderer with a CONSISTENT, ANIMATABLE asset set in one style, live on a 4 GB laptop with
free APIs. The missing piece is the asset/character layer: how to get (or make) a consistent, rigged,
multi-view library of people, animals, objects and places that covers open vocabulary, plus a fallback for
things outside the library that does not break the style. Options we have not fully tried: an existing free
rigged 2D/3D asset library (e.g. CC0 low-poly packs + Mixamo-style animations), generated SVG parts, a small
fixed core library + generated "props" only, or accepting a narrower scope.
